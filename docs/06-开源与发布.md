## 1. 许可证

**项目许可证：GNU General Public License v3.0 or later（`GPL-3.0-or-later`）**

已确认于 2026-11-07。仓库根目录 `LICENSE` 为官方 GPLv3 全文（35,149 字节，与 <https://www.gnu.org/licenses/gpl-3.0.txt> 完全一致）。

### 1.1 为什么选 GPL-3.0-or-later

| 理由 | 说明 |
|---|---|
| 防止闭源分叉 | 任何分发二进制的人都必须提供完整源代码，避免"拿去改个名字卖钱" |
| `or later` | 兼容未来的 GPLv4，给项目留出升级空间，同时不强制立即升级 |
| 与现有依赖兼容 | MIT / Apache-2.0 / BSD-2-Clause / OFL 均可与 GPLv3 组合 |
| 不需要 AGPL | 本项目是纯本地桌面软件，没有网络服务，AGPL 条款用不上 |
| 专利授权 | GPLv3 §11 含明示专利授权，对用户比 MIT 更有保障 |

### 1.2 分发义务清单

每次分发 usbscan 的**二进制**（安装包、zip、便携版）时，必须同时满足：

1. 附带 `LICENSE` 全文与版权声明。
2. 提供**完整对应源代码**（Corresponding Source），包含 `Cargo.lock`、构建脚本、`installer/`、`assets/` 生成脚本。
3. 若修改过源码，明确标注修改内容与日期。
4. 不得附加额外限制（不得要求用户先同意 EULA 才能行使 GPL 赋予的权利）。
5. 不得对源代码的接收者收取"源代码费用"（可收取介质成本）。

**推荐做法**：每个 GitHub Release 同时附上 `usbscan-<version>-source.tar.gz`，并在 Release 说明与 README 中写明"对应源代码可从本页面获取"。这满足 GPLv3 §6(d) 的"equivalent access"要求。

### 1.3 对二次开发者与集成方的影响

| 场景 | 是否允许 | 说明 |
|---|---|---|
| 个人/企业内部使用 | ✅ 无条件 | GPL 只约束"分发" |
| 修改后自用 | ✅ 无条件 | 无需公开 |
| 修改后分发（含免费分发） | ✅ 但必须开源 | 衍生作品整体按 GPLv3 授权 |
| 打包进商业产品分发 | ❌ 除非整体开源 | 不能与闭源代码静态/动态链接成一个作品 |
| 通过命令行调用 `usbscan.exe` | ⚠️ 需评估 | 若仅是进程间调用且不构成"结合成一个作品"，通常视为独立程序；但边界需谨慎 |
| 编写插件并动态加载进主程序 | ❌ 除非插件也是 GPL 兼容 | 动态链接通常被认定为衍生作品 |

> 若企业需要闭源集成，正确做法是**进程外调用**（命令行或本地 IPC），并在合同中明确二者是独立作品。

### 1.4 与其他组件的兼容性

| 组件许可证 | 与 GPLv3 组合 | 处理方式 |
|---|---|---|
| MIT / BSD-2 / BSD-3 | ✅ 兼容 | 直接链接，保留原版权声明 |
| Apache-2.0 | ✅ 兼容（GPLv3 明确允许） | 直接链接，保留 `NOTICE` |
| SIL OFL-1.1（字体） | ⚠️ 仅"聚合" | 字体作为独立文件随包分发，不并入二进制；字体本身仍受 OFL 约束 |
| tessdata | ✅ Apache-2.0 | 独立数据文件，随包分发并保留 LICENSE |
| GPL-2.0-only | ❌ 不兼容 | 禁止引入 |

> **字体特别注意**：界面字体子集若被**嵌入**到程序资源中并以 GPL 分发，会被视为"聚合"而非"结合"，通常可接受；但更稳妥的做法是把字体作为独立文件放在 `assets/fonts/` 并附 OFL 许可证。生成 PDF 时嵌入的字体属于文档的一部分，不受 GPL 影响。

### 1.5 落地动作

- [x] 仓库根目录放置 `LICENSE`（GPLv3 全文）
- [ ] `Cargo.toml` 声明 `license = "GPL-3.0-or-later"`
- [ ] 源文件头部添加 SPDX 标识（新文件强制，存量文件逐步补齐）：
      ```rust
      // SPDX-License-Identifier: GPL-3.0-or-later
      // Copyright (C) 2026 usbscan contributors
      ```
- [ ] README 顶部放置 GPLv3 徽章
- [ ] 关于对话框展示许可证名称与全文链接
- [ ] `THIRD_PARTY.md` 记录全部依赖与许可证
- [ ] Release 页面附源代码包
- [ ] CI 增加许可证检查（`cargo deny check licenses`）

### 1.6 贡献者授权

采用 **DCO（Developer Certificate of Origin）** 而非 CLA：

- 贡献者提交时使用 `git commit -s`，即表示同意 DCO 1.1。
- 不要求签署版权转让协议（CLA），降低贡献门槛。
- 由于采用 `or later`，未来若需升级到 GPLv4 无需回溯取得每位贡献者的同意。

> 注意：DCO 不改变版权归属，贡献者仍持有自己代码的版权，只是授权项目以 GPLv3+ 分发。

| `serde` / `toml` | 配置序列化 | MIT OR Apache-2.0 | 编译期内联 |
| `tracing` | 日志 | MIT | 编译期内联 |

| **Tesseract 5** | OCR 引擎 | Apache-2.0 | 静态链接 |
| **Leptonica** | Tesseract 依赖 | BSD-2-Clause | 静态链接 |
| **tessdata**（chi_sim, eng） | 语言模型 | Apache-2.0 | 随包分发 |
| 思源黑体（子集） | 界面/文档字体 | SIL OFL-1.1 | 随包分发 |
| PDF 生成库（TBD） | PDF 输出 | MIT / Apache-2.0 | 编译期内联 |
| 条码解码库（TBD） | 条码识别 | MIT / Apache-2.0 | 编译期内联 |
| Inno Setup | 安装包 | 自定义（允许自由分发） | 构建期工具 |

### 2.1 合规要求

1. 所有 MIT/Apache/BSD 组件的版权声明必须出现在 `THIRD_PARTY.md` 中。
2. Apache-2.0 组件需保留 `NOTICE`（如有）。
3. OFL 字体不得单独售卖，不得使用保留字体名称；作为独立文件随包分发，不并入二进制。
4. tessdata 的 Apache-2.0 要求保留 LICENSE 文件。
5. 生成 SBOM：`cargo cyclonedx` 输出 `sbom.json`，随 Release 附件发布。
6. **禁止引入 GPL-2.0-only、SSPL、BUSL 或任何与 GPLv3 不兼容的依赖**；CI 用 `cargo deny check licenses` 强制校验（白名单见 `deny.toml`）。
7. 新增依赖必须在 PR 中说明许可证，并同步更新 `THIRD_PARTY.md`。

## 3. 构建

### 3.1 环境要求

| 项 | 版本 |
|---|---|
| Rust | stable（`rust-toolchain.toml` 固定） |
| Visual Studio Build Tools | 2019 或 2022，含"使用 C++ 的桌面开发" |
| Windows SDK | 10.0.19041 以上 |
| LLVM（Tesseract 静态库） | 15+，或使用 vcpkg |

### 3.2 构建命令

```powershell
# 开发构建
cargo build

# 发布构建（静态 CRT）
$env:RUSTFLAGS = "-C target-feature=+crt-static"
cargo build --release -p usbscan-app --target x86_64-pc-windows-msvc
```

### 3.3 构建矩阵

| 产物 | target | 说明 |
|---|---|---|
| `usbscan-x64.zip` | `x86_64-pc-windows-msvc` | 主分发 |
| `usbscan-arm64.zip` | `aarch64-pc-windows-msvc` | Windows on ARM，可选 |
| `usbscan-x86.zip` | `i686-pc-windows-msvc` | 32 位，可选 |
| `usbscan-setup-x64.exe` | — | Inno Setup 安装包 |
| `usbscan-portable-x64.zip` | — | 便携版 |

### 3.4 可复现构建

- `Cargo.lock` 必须提交。
- 发布构建使用 `--locked`。
- `rust-toolchain.toml` 固定具体版本号（非 `stable`）。
- 记录构建环境（Rust 版本、SDK 版本、提交哈希）到 Release 说明。

## 4. CI

GitHub Actions，`windows-latest` runner。

```yaml
jobs:
  check:
    - cargo fmt --all -- --check
    - cargo clippy --workspace --all-targets -- -D warnings
    - cargo test --workspace
  build:
    - 构建 x64 release
    - 运行集成测试（mock 摄像头）
    - 上传 artifact
  package:
    - 生成 zip + 安装包
    - 生成 SBOM
    - 生成 SHA256SUMS
  release:
    - 仅在打 tag 时触发
    - 自动创建 GitHub Release
```

约束：

- PR 必须通过 `check`。
- 合并到 main 触发完整构建。
- `v*` 标签触发发布。

## 6. 代码签名与 SmartScreen

### 6.1 现状

- 开源项目通常无法负担 EV 证书（约 $300–500/年）。
- 无签名时，Windows SmartScreen 会对新发布版本弹"未知发布者"警告。
- 自签名证书无法通过 SmartScreen，且会触发更严格的警告。

### 6.2 策略

| 阶段 | 做法 |
|---|---|
| v0.x 测试版 | 不签名，README 中说明情况并提供 SHA256 校验方法 |
| v1.0 起 | 可选：申请 Azure Trusted Signing（成本较低）或由社区赞助 EV 证书 |
| 长期 | 积累下载量后 SmartScreen 信誉会自然提升 |

文档中必须明确告知用户"未签名"的原因与验证方法（`Get-FileHash`）。

## 7. 贡献指南

### 7.1 贡献流程

1. Fork → 创建分支 `feat/xxx` 或 `fix/xxx`。
2. 提交时使用 `git commit -s`，在提交信息末尾添加 `Signed-off-by`，表示同意 [DCO 1.1](https://developercertificate.org/)。
3. 提交前本地运行 `cargo fmt`、`cargo clippy -- -D warnings`、`cargo test`。
4. PR 描述需包含：改了什么、为什么、如何验证、截图（UI 变更）。
5. 至少一名维护者 review 后合并。

### 7.2 提交信息规范

```
<type>(<scope>): <subject>

type: feat | fix | docs | refactor | perf | test | chore | build
scope: capture | ui | imaging | ocr | naming | export | doc | win
```

示例：`feat(naming): 支持 {counter} 全局流水号`

### 7.3 代码要求

- 遵守 [02-架构设计 §11](02-架构设计.md#11-代码规范)。
- 新增功能必须附测试。
- 新增依赖必须更新第三方清单并确认许可证兼容。
- UI 变更必须附浅色/深色/高对比度三张截图。

### 7.4 Issue 模板

| 模板 | 必填内容 |
|---|---|
| Bug 报告 | 版本、系统版本、摄像头型号、复现步骤、日志、诊断包 |
| 功能请求 | 使用场景、期望行为、替代方案 |
| 摄像头兼容问题 | 设备型号、VID/PID、`设备管理器`截图、诊断包 |

### 7.5 行为准则

采用 Contributor Covenant v2.1。技术讨论对事不对人；不接受人身攻击、歧视性言论。

## 8. 隐私声明

usbscan 的设计承诺：

1. **不收集任何数据**。没有遥测、没有崩溃自动上报、没有使用统计。
2. **不主动联网**。启动、拍摄、处理、OCR、导出全程离线。
3. **唯一的网络行为**是用户点击"检查更新"时访问项目 Release 页面，可通过防火墙完全阻断而不影响功能。
4. **日志仅在本地**。默认不记录完整文件路径；用户主动导出诊断包时才产生外部文件。
5. **图像内容永不离开本机**。OCR 使用本地模型。

可在文档中提供验证方法：

```powershell
# 使用资源监视器或 TCPView 观察 usbscan.exe 的网络连接
# 预期：无任何连接（除手动检查更新时）
```

## 9. 版本策略

语义化版本 `MAJOR.MINOR.PATCH`：

| 变更 | 版本位 |
|---|---|
| 破坏性配置格式变更、移除功能 | MAJOR |
| 新增功能、新增配置项（向后兼容） | MINOR |
| Bug 修复、性能优化 | PATCH |

配置文件带 `version` 字段，升级时自动迁移，迁移前备份原文件。
